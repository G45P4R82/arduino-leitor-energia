# Experimento iot004 - Ethernet e OTA

## Objetivo

Validar uma placa ESP32/Wemos com shield Ethernet W5100 e criar um fluxo de atualizacao OTA usando GitHub Actions e GitHub Releases.

## Hardware testado

- ESP32 Wemos D1 R32
- Shield Ethernet W5100
- Arduino Mega 2560
- Sensor SCT-013

## Teste ESP32 + W5100

Firmware de diagnostico configurado com:

- SPI: SCK GPIO18, MISO GPIO19, MOSI GPIO23;
- CS: GPIO5;
- Sensor no GPIO36/ADC1;
- DHCP;
- Teste HTTPS via `SSLClient`;
- Trust anchors do GitHub.

Resultado:

```text
Hardware Ethernet: nao detectado
Link Ethernet: down
Falha no DHCP
```

O ESP32 foi detectado corretamente pela USB, leu o sensor, mas nao conseguiu conversar com o W5100 pelo SPI. Os LEDs do shield piscando confirmam apenas alimentacao/link fisico, nao comunicacao SPI.

Hipoteses:

- W5100 trabalha com logica de 5 V e ESP32 trabalha com 3,3 V;
- Falta de conversor de nivel logico;
- Shield W5100 pode nao ser eletricamente compativel com o ESP32;
- CS, SPI ou alimentacao podem estar incorretos.

## Teste Mega + W5100

O Arduino Mega foi testado com o mesmo shield.

Resultado:

```text
DHCP: OK
IP: 192.168.15.19
Sensor: leitura de corrente funcionando
```

O Mega e eletricamente compativel com o W5100 e resolve a comunicacao basica Ethernet.

## Teste TLS no Mega

Foi instalada e testada a biblioteca `SSLClient` sobre `EthernetClient`.

A compilacao falhou inicialmente por falta de `std::vector` no ambiente AVR. Um shim experimental permitiu chegar ao calculo de memoria, mas o resultado foi:

```text
Flash utilizada: 168594 bytes
SRAM utilizada: 26981 bytes
SRAM disponivel no Mega: 8192 bytes
```

Resultado: TLS seguro nao cabe no Mega. A SRAM necessaria ultrapassa em muito a capacidade da placa.

## Teste HTTP sem TLS

Foi verificado que os enderecos HTTP do GitHub redirecionam para HTTPS:

```text
HTTP 301 -> HTTPS
```

Portanto, remover o TLS nao resolve o acesso direto ao GitHub. Mesmo que um servidor HTTP local fosse usado, o Mega ainda nao possui um bootloader OTA para gravar uma nova aplicacao com seguranca.

## Conclusao

```text
Mega + W5100 + Ethernet: funciona
Mega + W5100 + TLS: inviavel por memoria
Mega + W5100 + OTA seguro: nao funciona com bootloader padrao
ESP32 + W5100 direto: problema de niveis logicos/SPI
```

O bypass do TLS remove a criptografia, mas nao resolve a ausencia de mecanismo de gravacao OTA no Mega.

## Alternativas

### ESP32 + W5500

Alternativa recomendada. O W5500 deve ser compativel com logica de 3,3 V e o ESP32 possui memoria, particoes OTA e recursos para TLS.

### ESP32 + W5100 com conversor

Pode funcionar se todas as linhas SPI forem adaptadas de 5 V para 3,3 V e o mapeamento de CS/SPI estiver correto.

### ESP32 como gateway

O ESP32 baixa o firmware via HTTPS e grava o Mega pela serial ou ICSP. Exige conexao fisica entre as placas e adaptacao de nivel.

### Mega com OTA HTTP customizado

Possivel apenas com bootloader customizado, protocolo proprio e risco de inutilizar a placa em caso de interrupcao. Nao recomendado para producao.

## Registro completo dos experimentos

### 1. Identificacao da Wemos

A placa ESP32 foi detectada pela USB usando conversor CH340 em `/dev/ttyUSB0`.

Identificacao obtida:

- Chip: ESP32-D0WD-V3;
- Revisao: 3.1;
- Flash: 4 MB;
- Wi-Fi e Bluetooth disponiveis;
- MAC registrado durante o teste: `cc:db:a7:3d:fd:c0`.

O perfil Arduino usado foi `esp32:esp32:esp32`.

### 2. Leitura analogica no GPIO2

Foi gravado um firmware temporario para medir o GPIO2 como ADC.

Resultados observados:

```text
ADC bruto: aproximadamente 280 a 406
Tensao: aproximadamente 0,41 a 0,51 V
```

Conclusao: havia sinal analogico no GPIO2.

Problema identificado: GPIO2 pertence ao ADC2 do ESP32. ADC2 entra em conflito com o Wi-Fi e nao deve ser usado para o sensor quando a comunicacao Wi-Fi esta ativa.

### 3. Leitura de corrente no GPIO2

Foi usado `EmonLib` no GPIO2 com calibracao `6.0606`.

Resultados:

```text
0,639 A
0,180 A
0,095 a 0,102 A
```

Conclusao: o sensor podia ser convertido para amperes, mas o GPIO2 nao era adequado para o firmware com Wi-Fi.

### 4. Mudanca para GPIO36

O sensor foi movido para `IO36/GPIO36/ADC0`, que pertence ao ADC1.

Com o Wi-Fi ativo, a Wemos passou a medir aproximadamente:

```text
1,27 a 1,38 A
```

O canal pessoal ThingSpeak recebeu entradas com sucesso. Essa foi a configuracao analogica adotada para o ESP32.

### 5. Testes de credenciais Wi-Fi

Foram testadas diferentes combinacoes de SSID e senha por causa da sensibilidade a maiusculas e minusculas. Uma combinacao conectou e publicou no ThingSpeak; outras produziram mensagens de falha de conexao.

Conclusao: o ESP32 e capaz de conectar e publicar quando as credenciais exatas sao usadas. As credenciais nao sao registradas neste documento.

### 6. Publicacao dupla do iot003

O firmware foi alterado para publicar a mesma telemetria em dois canais:

- Canal pessoal `3511204`;
- Canal IC `3513189`.

Resultados observados:

- Os dois canais receberam entradas;
- Os oito Fields foram enviados;
- `field8=1` indicou Wi-Fi ativo;
- Falhas ficaram em zero durante o teste.

Conclusao: a publicacao dupla funciona via Wi-Fi no ESP32.

### 7. Primeiro teste ESP32 + W5100

Foi criado um firmware de diagnostico para:

- SPI em GPIO18, GPIO19 e GPIO23;
- CS em GPIO5;
- DHCP;
- Leitura do sensor no GPIO36;
- Deteccao de hardware Ethernet;
- Teste HTTPS contra o GitHub.

Resultado repetido:

```text
Hardware Ethernet: nao detectado
Link Ethernet: down
Falha no DHCP
```

Conclusao: o cabo e os LEDs nao foram suficientes para provar comunicacao SPI com o W5100.

### 8. Hipotese de incompatibilidade eletrica

O W5100 foi projetado para shields Arduino de 5 V, enquanto o ESP32 usa logica de 3,3 V.

Foi identificada a necessidade potencial de:

- Conversor de nivel para SPI;
- Alimentacao correta;
- CS correto;
- GND comum;
- Ligacao SPI correta.

Nenhum cheiro ou aquecimento anormal foi observado, mas isso nao comprova seguranca dos GPIOs.

### 9. Teste com IP fixo

Foram testados IPs fixos na rede `192.168.15.0/24`, com gateway `192.168.15.1`.

Resultado:

- O firmware configurou IP;
- O W5100 continuou sem ser detectado em alguns testes;
- A conexao TCP com ThingSpeak falhou.

Conclusao: trocar DHCP por IP fixo nao resolveu a comunicacao SPI/rede do ESP32 com o W5100.

### 10. Teste Arduino Mega + W5100

O W5100 foi conectado a um Arduino Mega 2560.

Resultado:

```text
DHCP: OK
IP: 192.168.15.19
Sensor: leitura de corrente funcionando
```

Conclusao: o W5100 funciona com uma placa Arduino de logica 5 V. Isso reforcou a hipotese de incompatibilidade direta com o ESP32.

### 11. Teste TLS no Mega

A biblioteca `SSLClient` foi testada sobre `EthernetClient`.

Resultados:

- O AVR nao possuia `std::vector` no ambiente padrao;
- Foi criado um shim experimental apenas para avaliar a compilacao;
- O uso final ficou em aproximadamente 26.981 bytes de SRAM;
- O Mega possui somente 8.192 bytes de SRAM.

Conclusao: HTTPS/TLS seguro nao cabe no Mega de forma viavel.

### 12. Teste de HTTP sem TLS

Foi testado o acesso HTTP ao GitHub.

Resultado:

```text
HTTP 301 -> HTTPS
```

Conclusao: remover TLS nao permite acessar diretamente os assets do GitHub Release. Alem disso, o bootloader padrao do Mega nao possui mecanismo de atualizacao OTA.

### 13. CI/CD e GitHub Release

O repositorio foi tornado publico para permitir distribuicao dos assets de Release.

Foi criado o workflow `.github/workflows/iot004.yml` com:

- Validacao em Pull Request;
- Build para ESP32;
- Particao OTA;
- Tags no formato `iot004-vX.Y.Z`;
- Verificacao de tag pertencente a `main`;
- Geracao de binario;
- SHA-256;
- Manifesto;
- Assinatura RSA;
- Publicacao automatica em GitHub Release.

O secret `IOT004_OTA_SIGNING_KEY` foi cadastrado no GitHub. A chave publica foi adicionada ao firmware.

O cliente OTA ainda nao esta habilitado porque a deteccao do W5100 no ESP32 falhou. O proximo teste deve resolver primeiro a camada eletrica/SPI e validar:


Somente depois desses resultados o download, a validacao e a gravacao OTA devem ser ativados.
